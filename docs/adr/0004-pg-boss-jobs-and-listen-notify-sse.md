# Background jobs on pg_boss, live updates over LISTEN/NOTIFY and SSE

Asynchronous work runs on **pg_boss** against the same Postgres instance as everything else, rather than Redis/BullMQ or a hosted queue. Postgres is already a hard dependency, so this adds no new service to operate, jobs are durable rows (a job enqueued before a restart is still there afterwards), and a job can be enqueued in the same database as the row it is about. The cost is that pg_boss is polling-based and does not scale to very high job rates — acceptable for a pipeline whose unit of work is "convert a document", measured in seconds.

The ingestion pipeline is **one queue per stage, chained**: each stage is retried independently, and on success enqueues the next. A later stage's bug therefore never re-runs an expensive earlier stage, and each stage's retry policy and timeout can differ. The alternative — one job that runs the whole pipeline — would make a failure in the last step repeat all the work before it.

**Docling runs as a spawned Python subprocess**, one per conversion, not as a long-lived sidecar service. The backend downloads the raw file from object storage to a temp path and passes the subprocess a second temp path to write to; the Markdown is read back from that *file*, never from stdout. Reasons: Docling and its Python dependencies write warnings and progress to stdout, which would corrupt the output; a file survives this process dying after the subprocess succeeded, so a retried job can still pick the result up; and a Docling crash on a malformed input takes down one job attempt instead of a shared service. Process startup is noise next to the conversion itself, since this is already a batch job.

Live updates are published via **Postgres `LISTEN`/`NOTIFY`** and forwarded to clients over **server-sent events**. NOTIFY rather than an in-process emitter because the pg_boss worker that publishes an event and the HTTP process holding a client's SSE connection need not be the same process (and in a scaled-out deployment are not) — Postgres is the bus both already share. SSE rather than WebSockets because every flow here is server→client only, and SSE is plain HTTP: the session cookie, CORS, and the auth guard all apply unchanged, and browsers reconnect on their own.

The event channel is **generic**, not ingestion-specific: one NOTIFY channel, one `GET /events` endpoint, one event envelope (`type`, `topic`, `data`). Later features — chat answer streaming, other background-task progress — publish onto it without new transport. Two consequences follow from NOTIFY's semantics and are deliberate: a payload must stay well under Postgres's 8000-byte NOTIFY cap, so events carry *what changed* and not bulk data; and there is no replay, so an event is a hint and a reconnecting client re-reads current state over the normal API.
