# Exact vector scan instead of an approximate-nearest-neighbour index

Search (NBK-9) ranks Chunks with an exact scan over `chunks.embedding`, with no ANN index — the decision migration `0007` deferred "for the retrieval ticket, with real data to measure". Three measured facts settle it. First, pgvector refuses HNSW and ivfflat above 2000 dimensions and these vectors are 2560, so the only index available at all is a duplicated `halfvec(2560)` column with HNSW on it. Second, an HNSW index cannot accelerate the query this feature actually runs: ranking per Document means `MIN(distance) ... GROUP BY`, and an ANN index serves only `ORDER BY ... LIMIT k`, so adopting it means replacing "every Document's best Chunk" with "the Documents owning the globally top-k Chunks" — different results, not the same results faster, and measured at 2/10 agreement with the exact top ten on a 70,000-chunk corpus. Third, the exact scan is not the bottleneck at realistic sizes: 10 ms for one 150-page Document's 700 Chunks and 62 ms for ten of them, against a ~400 ms OpenRouter round trip to embed the query in the same request. The trade-off is that latency grows linearly with a Notebook's Chunk count — about 0.5 s at 35,000 Chunks and 1.1 s at 70,000 — so a Notebook holding a hundred 150-page Documents will feel slow. The cheapest next step when that happens is a `halfvec(2560)` column with no index at all (28% faster, measured, with an identical top ten because it is still exact), and only then the ANN rewrite, which needs a recall measurement against real embeddings rather than the random vectors used here. `docs/search.md` records the full measurement.
